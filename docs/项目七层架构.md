# DrinkMind 项目七层架构

这份文档记录的是当前代码的真实状态，不是理想架构图，也不是简历包装。

当前后端已经完成 Phase 1A 到 Phase 2E 的分层整理。现在大体是：

```text
backend/main.py              app 启动入口
backend/api/schemas.py       API 请求模型
backend/api/routers/         Controller 层
backend/services/            业务服务层
backend/agents/              AI、Agent、Workflow、RAG、Rules 能力
backend/database.py          ORM models、DB session、migration
```

简单说：现在请求先进 router，router 调 service，service 再调 agents 和 database。`main.py` 已经不再堆业务流程。

## 1. Interface / API 层

### 这一层负责什么

这一层负责接住前端请求，并把请求交给后面的业务服务。

它应该做：

- 定义接口路径。
- 接收 request。
- 注入数据库 session。
- 调用 service。
- 返回 service 给的结果。

它不应该做很多业务判断，也不应该直接写一大段数据库流程。

### 当前项目对应哪些文件

- `backend/main.py`
- `backend/api/schemas.py`
- `backend/api/routers/logs.py`
- `backend/api/routers/knowledge.py`
- `backend/api/routers/agent.py`
- `backend/api/routers/health.py`

### 这些文件现在是否已经在合适位置

基本合适。

`main.py` 现在主要负责：

- 创建 `FastAPI` app。
- 配置 CORS。
- 初始化数据库。
- 注册 routers。
- 挂载静态文件。
- 本地启动时跑 `uvicorn`。

`api/schemas.py` 现在放 request schema，也就是接口入参模型。

`api/routers/*` 现在主要是 Controller。它们还不是完全零逻辑，但已经比之前清楚很多。

### 如果以后重构，建议迁移到哪里

这层目前不用大迁移。

后面如果继续整理，可以做：

- `health.py` 继续变薄。
- router 里重复的 endpoint helper 再慢慢下沉到 service。
- schema 如果变太多，可以按业务拆成多个 schema 文件。

### 注意事项

- API path 不要随便改，前端已经依赖这些路径。
- response shape 不要随便改，测试和前端都可能依赖。
- router 里不要再新增大段业务流程，优先写到 service。

## 2. Orchestration / Workflow 层

### 这一层负责什么

这一层负责“流程怎么走”。

它决定：

- 先解析用户输入，还是先查知识库。
- 命中知识库后怎么处理。
- 估算失败时怎么降级。
- 用户意图是记录饮品、聊天建议，还是生成健康计划。
- 哪些 Agent 或工具要参与。

### 当前项目对应哪些文件

- `backend/agents/orchestrator.py`
- `backend/agents/nutrition_pipeline.py`
- `backend/services/agent_action_service.py`
- `backend/services/chat_service.py`
- `backend/services/drink_log_service.py`
- `backend/services/knowledge_acquisition_service.py`

### 这些文件现在是否已经在合适位置

大体可以接受。

`orchestrator.py` 和 `nutrition_pipeline.py` 仍在 `agents` 目录里，因为它们和 Agent 能力关系很近。

service 层现在承担了不少业务流程编排，比如：

- 创建饮品记录时调用营养估算。
- 聊天时保存消息、解析 intake、生成回复、写 trace。
- agent act 时调用 orchestrator、memory、health plan。
- evidence 审核后写入正式知识库。

### 如果以后重构，建议迁移到哪里

当前不用新建很重的 `workflows` 目录。

如果以后流程越来越多，可以考虑：

```text
backend/workflows/nutrition_workflow.py
backend/workflows/agent_workflow.py
```

但现在先放在 `agents` 和 `services` 里就够了。

### 注意事项

- 不要为了分层强行把一个清楚的流程拆碎。
- `nutrition_pipeline.py` 的行为很关键，composition eval 会保护它。
- `orchestrator.py` 暂时不要动内部行为。

## 3. Agent / Reasoning 层

### 这一层负责什么

这一层负责理解、推理、生成。

包括：

- 解析自然语言饮品。
- 判断用户意图。
- 生成陪伴式聊天回复。
- 生成健康计划。
- 生成日报和周报。
- 从用户话语里提取记忆。

### 当前项目对应哪些文件

- `backend/agents/intake_parser.py`
- `backend/agents/companion_agent.py`
- `backend/agents/nutrition_agent.py`
- `backend/agents/orchestrator.py`
- `backend/agents/health_plan_agent.py`
- `backend/agents/report_agent.py`
- `backend/agents/memory_agent.py`
- `backend/agents/llm_config.py`

### 这些文件现在是否已经在合适位置

暂时可以接受。

不完美的地方是：

- `memory_agent.py` 既做记忆逻辑，也直接碰数据库。
- `health_plan_agent.py` 既生成计划，也保存计划。
- `report_agent.py` 更像报告服务，但现在还在 agents。
- `llm_config.py` 更像基础配置。

这些现在不是最大问题，可以暂缓。

### 如果以后重构，建议迁移到哪里

可以先不动。

以后如果要更清楚，可以考虑：

```text
backend/services/health_plan_service.py
backend/services/report_service.py
backend/services/memory_service.py
backend/core/llm.py
```

### 注意事项

- 不要把可离线跑的解析逻辑改成必须调用大模型。
- 不要改 LangGraph 或 orchestrator 行为。
- Agent 层现在是核心能力层，先保护行为稳定。

## 4. Tools / Rules / Retrieval 层

### 这一层负责什么

这一层负责可复用的工具能力。

包括：

- 成分估算。
- 糖和咖啡因规则。
- 风险提示。
- 知识库查找。
- RAG / Chroma 同步和检索。
- 图片分析和证据抽取。

### 当前项目对应哪些文件

- `backend/local_estimator.py`
- `backend/agents/composition_agent.py`
- `backend/agents/ingredient_rules.py`
- `backend/agents/risk_agent.py`
- `backend/agents/knowledge_lookup.py`
- `backend/agents/rag_store.py`
- `backend/agents/knowledge_acquisition_agent.py`

### 这些文件现在是否已经在合适位置

能用，但命名还比较混。

`composition_agent.py` 和 `ingredient_rules.py` 虽然在 agents 目录，但实际更像规则引擎。

`knowledge_lookup.py` 和 `rag_store.py` 更像 knowledge / retrieval 层。

`knowledge_acquisition_agent.py` 现在仍然比较大，里面有搜索、图片导入、候选、证据、审核相关能力。

### 如果以后重构，建议迁移到哪里

以后可以考虑：

```text
backend/rules/composition.py
backend/rules/ingredients.py
backend/rules/risk.py
backend/knowledge/lookup.py
backend/knowledge/rag_store.py
backend/knowledge/acquisition.py
```

现在先不拆。

### 注意事项

- composition 和 nutrition pipeline 是项目核心，不要顺手改公式。
- RAG / Chroma 行为不要在普通分层整理里改。
- knowledge acquisition 逻辑复杂，拆之前要先补好验收点。

## 5. Knowledge / Memory 层

### 这一层负责什么

这一层负责项目“知道什么”和用户“长期偏好是什么”。

包括：

- 正式饮品知识库。
- 候选饮品。
- 营养证据。
- 用户偏好。
- 聊天历史。
- 饮品日志。
- 睡眠记录。
- Agent trace。
- Chroma 向量库。

### 当前项目对应哪些文件

- `backend/database.py`
- `backend/services/knowledge_service.py`
- `backend/services/knowledge_acquisition_service.py`
- `backend/services/user_preference_service.py`
- `backend/agents/knowledge_lookup.py`
- `backend/agents/rag_store.py`
- `backend/agents/memory_agent.py`
- `backend/chroma_db`
- `drinks.db`

### 这些文件现在是否已经在合适位置

部分合适。

知识库 CRUD 和 acquisition 工作流已经进了 service。

用户偏好入口也已经从 router 抽到了 `user_preference_service.py`。

但 `database.py` 仍然是一个总入口，里面放了：

- ORM models。
- DB session。
- init_db。
- 自动迁移。

这不是最终形态，但目前先保留。

### 如果以后重构，建议迁移到哪里

以后可以拆成：

```text
backend/db/session.py
backend/db/models/
backend/db/migrations.py
```

但建议保留 `backend/database.py` 作为兼容入口，继续 re-export 原来的名字。

### 注意事项

- 现在 services 直接用 SQLAlchemy，这是有意保留的。
- 当前阶段不抽 repository。
- 拆 `database.py` 风险比拆 router/service 高，需要单独做。
- SQL 知识库和 Chroma 要保持同步。

## 6. Guardrails / Verification 层

### 这一层负责什么

这一层负责让输入输出不要太离谱。

包括：

- request 字段范围。
- 图片大小和类型限制。
- 来源域名限制。
- feedback 修正值校验。
- 估算结果解释。
- 离线模式控制。
- 风险和提醒。

### 当前项目对应哪些文件

- `backend/api/schemas.py`
- `backend/services/nutrition_feedback_service.py`
- `backend/services/knowledge_acquisition_service.py`
- `backend/agents/nutrition_pipeline.py`
- `backend/agents/knowledge_acquisition_agent.py`
- `backend/agents/llm_config.py`
- `backend/agents/risk_agent.py`

### 这些文件现在是否已经在合适位置

基本可接受。

现在校验分布在 schema、service、agent 里：

- 请求形状在 `api/schemas.py`。
- feedback 业务校验在 `nutrition_feedback_service.py`。
- acquisition 请求限制在 `knowledge_acquisition_service.py` 和 agent 里。
- LLM 开关在 `llm_config.py`。

### 如果以后重构，建议迁移到哪里

暂时不建议单独建一个很重的 guardrails 目录。

以后如果校验越来越多，可以考虑：

```text
backend/services/validation_service.py
backend/rules/risk.py
```

### 注意事项

- 错误码和错误信息不要随便变。
- feedback 的 corrected values 校验不能丢。
- 离线控制不能丢，测试会覆盖。
- 解释字段会影响前端展示。

这一层负责看系统有没有跑对，以及出问题时能不能追踪。

包括：

- 单元测试。
- API 测试。
- composition eval。
- Agent trace。
- nutrition graph trace。
- quality gate。

### 当前项目对应哪些文件

- `backend/tests/`
- `backend/tests/run_composition_eval_report.py`
- `backend/tests/fixtures/composition_eval_cases.json`
- `backend/services/trace_service.py`
- `backend/database.py` 里的 `AgentTrace`
- `backend/agents/nutrition_pipeline.py` 里的 `graph_trace`
- `scripts/quality_gate.ps1`

### 这些文件现在是否已经在合适位置

比之前清楚很多。

trace 保存和查询已经从 router 抽到 `trace_service.py`。

测试仍然集中在 `backend/tests`，这没问题。

### 如果以后重构，建议迁移到哪里

当前不急。

以后如果 eval 变多，可以考虑：

```text
backend/evals/
```

但现在 `backend/tests/run_composition_eval_report.py` 继续保留即可。

### 注意事项

- 每次改 nutrition pipeline 都要跑 composition eval。
- 每次改 API 层都要跑 quality gate。

## 暂时不拆的东西

### `database.py` 暂时仍作为 DB 入口

它确实偏大，但它是全项目的老入口。

现在先不拆，是为了避免一次性影响太多 import、建表和测试。

### services 暂时直接用 SQLAlchemy

当前没有抽 repository。

这是刻意保持简单。现在项目规模还可以接受，先把 router 变薄更重要。

### agents 目录暂时继续混放多种 AI 能力

`agents` 里现在还有：

- LangGraph / workflow。
- LLM。
- composition。
- RAG。
- rules。
- memory。

这不完美，但现在先不要继续拆。先让 API 和 service 层稳定。

### `backend/agent.py` 是 legacy facade

如果这个文件仍然存在，它的定位是兼容入口。

也就是说，旧测试或旧 import 还可以从这里拿函数，但新功能不要继续往这里加。

新代码应该优先放到：

- `backend/api/routers`
- `backend/services`
- `backend/agents`

## 下一步可选优化

### 1. `health.py` service 化

这是下一步最自然的整理点。

可以抽：

```text
backend/services/health_plan_service.py
backend/services/report_service.py
```

### 2. `database.py` 拆 models / session / migration

这一步有风险，建议单独做。

目标不是删除 `database.py`，而是让它逐步变成兼容出口。

### 3. 清理 Pydantic `.dict()` warning

现在 quality gate 会出现 Pydantic v2 的 `.dict()` deprecation warning。

这不是行为 bug，但后面可以统一改成 `model_dump()`。

### 4. agents 目录进一步分组

可以考虑拆成：

```text
backend/agents/
backend/rules/
backend/knowledge/
```

但现在暂缓。因为这里牵动 nutrition pipeline、RAG、knowledge acquisition，风险比 router/service 大。

## 我应该从哪里开始读代码

如果你想理解项目，不建议从 `database.py` 一头扎进去。

推荐顺序：

1. 先读 `backend/main.py`，知道 app 怎么启动、router 怎么挂上去。
2. 再读 `backend/api/routers/logs.py`，看手动记录饮品的入口。
3. 接着读 `backend/services/drink_log_service.py`，看记录怎么创建、怎么调用营养估算。
4. 再读 `backend/agents/nutrition_pipeline.py`，看咖啡因和糖怎么估。
5. 然后读 `backend/api/routers/agent.py`，看聊天和 agent action 的入口。
6. 接着读 `backend/services/chat_service.py` 和 `backend/services/agent_action_service.py`。
7. 再读 `backend/agents/orchestrator.py`、`intake_parser.py`、`companion_agent.py`。
8. 想看知识库，再读 `backend/api/routers/knowledge.py`。
9. 接着读 `backend/services/knowledge_service.py` 和 `knowledge_acquisition_service.py`。
10. 最后再读 `backend/database.py`，把表结构和前面的流程对上。

如果只想先搞懂主流程，就先看：

```text
main.py
-> logs.py
-> drink_log_service.py
-> nutrition_pipeline.py
-> database.py
```
